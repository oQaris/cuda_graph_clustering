# cuda_graph_clustering — корреляционная кластеризация графа на GPU

Пакет решает задачу **нестрогой k-корреляционной кластеризации**: разбить вершины
графа не более чем на k кластеров так, чтобы число «разногласий» было минимально.
Разногласие — это пара вершин, которая либо соединена ребром и разнесена по разным
кластерам, либо не соединена и попала в один кластер.

Алгоритм — **PBILS** (population based iterated local search), перенесённый на CUDA.
Пакет самодостаточен: он собирается из файлов только этого репозитория и ничего
не линкует из чужих проектов. Исходный алгоритм, который здесь портирован, живёт
отдельно: <https://github.com/BIGADIL/graph_correlation_clustering>.

## Постановка

| Что                              | Как                                                                                                     |
|----------------------------------|---------------------------------------------------------------------------------------------------------|
| Число кластеров                  | нестрогое: не более k, пустые кластеры допустимы. k произвольное, не только 2 и 3                       |
| Ограничения на размеры кластеров | нет                                                                                                     |
| Граф                             | невзвешенный, неориентированный, без петель                                                             |
| Целевая функция                  | число разногласий, минимизация, целочисленная                                                           |
| Бейзлайн для сравнения           | PBILS из `BIGADIL/graph_correlation_clustering` (в конфигах назван `Genetic`, в коде — `IPLSAlgorithm`) |

Шаг GWW (замена худших решений копиями лучших) добавляется в цикл `SolveGpu` одним ядром,
когда придёт время это проверить.

## Математика

Пусть **A** — матрица смежности, **Z** — матрица назначений n×k (в строке v единица
в столбце того кластера, куда назначена вершина), n_c — размеры кластеров,
m — число рёбер. Тогда целевая функция:

```
f = m + Σ_c C(n_c, 2) − tr(ZᵀAZ)
```

Это и есть «матричное вычисление целевой функции»: считать надо не пары вершин,
а произведение матриц. Ключевой объект — матрица связей

```
G = A·Z,     G[v][c] = число соседей v в кластере c
```

Через неё выигрыш от переноса одной вершины считается за O(1):

```
Δf(v: a → c) = (n_c − n_a + 1) − 2·(G[v][c] − G[v][a])
```

то есть полная таблица выигрышей для всех n·k возможных ходов — это одно матричное
произведение, а после хода G правится за O(n): меняются только два столбца.

Для невзвешенного графа произведение A·Z выгоднее считать не через GEMM, а
побитово: строка A хранится упакованной по битам, кластер — битовой маской, и
G[v][c] = Σ popcount(A_row_v & mask_c). Это 32 сравнения пар за одну инструкцию.
Путь через тензорные ядра (cuBLAS, batched GEMM по всей популяции) остаётся
следующим шагом и станет обязательным, если граф станет взвешенным — там popcount
уже не применить.

Формула и её инкрементальная версия лежат в `include/cc_math.hpp` и компилируются
и для хоста, и для устройства, поэтому CPU-референс и ядра CUDA физически не могут
разойтись в арифметике.

## Устройство GPU-версии

**Один блок на особь популяции.** Каждая особь идёт по своей цепочке локального
поиска независимо, синхронизация между блоками внутри итерации не нужна. Размер
популяции — тот самый параметр, который автор бейзлайна не мог увеличить на CPU, —
становится источником параллелизма: популяция 4096 занимает 4096 блоков.

Внутри блока потоки делят между собой вершины: оценивают все n·k ходов по
поддерживаемой матрице G, редукцией находят наилучший, применяют его и правят G
за O(n) слитными обращениями к памяти.

**Раскладка памяти** подобрана под это разбиение: внутри решения данные лежат
подряд по вершинам (`labels[sol][v]`, `g[sol][c][v]`), поэтому шаговый доступ
потоков блока сливается в один запрос. Обратная раскладка — с чередованием особей,
когда соседние адреса принадлежат разным решениям, — выгодна там, где одному
потоку принадлежит целое решение; здесь целое решение принадлежит блоку, и
выгодна именно эта.

Одна итерация PBILS (как в бейзлайне):

1. `KernelSelect` — турнирная селекция; победитель копируется вместе с G и
   размерами кластеров, поэтому пересчёт не нужен;
2. `KernelLocalSearch` — наискорейший спуск по одиночным переносам до локального
   оптимума;
3. рекорд снимается на хосте (копируются P значений f, при улучшении — метки);
4. `KernelPerturb` + `KernelRebuild` — случайное возмущение и пересчёт G.

Останов — по числу итераций без обновления рекорда (`--early-stop`) или по лимиту
времени (`--time-limit`).

## Многопоточность CPU-версии

Ось параллелизма та же, что и на GPU: слоты популяции внутри одной итерации
независимы — каждый читает общую популяцию и пишет только свою ячейку следующей.
Где GPU даёт слоту блок, CPU даёт ему поток из пула (`--threads`, по умолчанию 1,
`0` — по числу ядер). Итерация разбита на две фазы — «селекция + локальный поиск»
и «возмущение + пересчёт G», а между ними главный поток снимает рекорд, пока
локальные оптимумы ещё не испорчены возмущением. Слоты раздаются атомарным
счётчиком, а не равными диапазонами: локальный поиск у разных особей сходится
за разное число ходов.

У каждого слота свой поток ГПСЧ, выведенный из `(seed, slot, итерация)`, а не взятый
из общего последовательного состояния, поэтому **ответ не зависит от числа потоков**.
Схема вывода сидов совпадает с ядрами CUDA, а правила разрешения ничьих в локальном
поиске у бэкендов одинаковы (меньший номер вершины, затем меньший номер кластера),
поэтому при одинаковых параметрах и `--seed` **CPU и GPU идут по одной траектории** и
выдают одно и то же значение целевой функции за одно и то же число итераций — во всём
диапазоне, где GPU-версия вообще работает: при n > 32 767 она отказывает (16-битные
счётчики G), а не расходится молча. Проверено на k = 2 и 3, n до 8 000, популяциях 128–1 024.
Это и делает сравнение времён честным: стороны делают буквально одну и ту же работу.

## Сборка

```bash
make            # CPU-часть; GPU-часть, если найден nvcc
make cpu        # референс + тесты, обычный C++17, CUDA не нужна
make gpu        # решатель на CUDA        (нужен nvcc; арка: GPU_ARCH=sm_80 make gpu)
make test       # проверки корректности математики
```

`GPU_ARCH` обязан соответствовать карте. По умолчанию `sm_70`: на более новой
карте это не ошибка сборки, но драйвер будет каждый запуск компилировать ядра из
PTX, и мерить вы будете JIT-код. `sm_75` Turing, `sm_80` A100, `sm_86` Ampere
GeForce, `sm_89` Ada, `sm_90` Hopper.

### Windows

`make` здесь нет, а `nvcc` на Windows требует хостовым компилятором MSVC, так
что нужны **VS Build Tools** с рабочей нагрузкой «Разработка классических
приложений на C++» (даёт `cl.exe` и Windows SDK) и **CUDA Toolkit**. Компиляторы
вызываются напрямую, из окружения `vcvars64.bat`:

```bat
call "C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\VC\Auxiliary\Build\vcvars64.bat"

mkdir bin obj

cl /nologo /O2 /std:c++17 /EHsc /arch:AVX2 /DNDEBUG /Iinclude ^
   src\cc_graph.cpp src\cc_pbils_cpu.cpp src\main_cpu.cpp ^
   /Fe:bin\cc_cpu.exe /Foobj\

cl /nologo /O2 /std:c++17 /EHsc /arch:AVX2 /DNDEBUG /Iinclude ^
   src\cc_graph.cpp src\cc_pbils_cpu.cpp src\cc_verify.cpp ^
   /Fe:bin\cc_verify.exe /Foobj\

nvcc -O3 -std=c++17 -Iinclude --generate-code arch=compute_89,code=sm_89 ^
   -Xcompiler "/O2 /std:c++17 /EHsc /arch:AVX2 /DNDEBUG" ^
   -o bin\cc_gpu.exe cuda\cc_pbils_gpu.cu cuda\main_gpu.cu ^
   src\cc_graph.cpp src\cc_pbils_cpu.cpp
```

## Запуск

У CPU- и GPU-бинарников одинаковый интерфейс, поэтому их можно сравнивать
напрямую:

```bash
# сгенерировать инстанс по сиду и решить
./bin/cc_cpu --n 3000 --density 0.33 --graph-seed 7 --k 3 --pop 128 --runs 10
./bin/cc_gpu --n 3000 --density 0.33 --graph-seed 7 --k 3 --pop 4096 --runs 10

# тот же прогон на всех ядрах CPU и он же на GPU: один `--seed` — одна траектория,
# так что сравнивается ровно одна и та же работа
./bin/cc_cpu --n 2000 --graph-seed 7 --k 3 --pop 128 --seed 5 --threads 0
./bin/cc_gpu --n 2000 --graph-seed 7 --k 3 --pop 128 --seed 5

# решить инстанс, на котором гоняли бейзлайн: граф лежит в его же файле результатов
./bin/cc_gpu --graph-json ../graph_correlation_clustering/non_strict_2cc/n-600-p-0.67/n-600-p-0.67-12345.json

# сохранить инстанс, чтобы отдать его бейзлайну
./bin/cc_gpu --n 600 --density 0.33 --graph-seed 1 --save-graph-json inst.json
```

Полный список опций — `--help`. Значение целевой функции по умолчанию **всегда**
перепроверяется независимым пересчётом по парам за O(n²); расхождение — это выход
с кодом 2, а не предупреждение.

## Измеренная производительность

RTX 4070 Ti SUPER (Ada, 66 SM) против Ryzen 7 3700X (8 ядер / 16 потоков),
CUDA 13.3, MSVC 19.44, инстансы G(n, p) при p = 0,33.

| Сравнение                                                                                         | Результат                                                                                                                                                                                                       |
|---------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `cc_gpu` против `cc_cpu` (одинаковые параметры, k = 3, популяция 128)                             | 86–581× по времени. Ускорение **немонотонно**: максимум 581× на n = 6 000, дальше падает — при большем n одному блоку нужно больше половины разделяемой памяти SM, и резидентных блоков становится вдвое меньше |
| `cc_gpu` против многопоточного оригинала (16 потоков, его же параметры и его собственный останов) | примерно 174–498× по времени, растёт с размером, при сопоставимом качестве. Точность ограничена тем, что оригинал рапортует время целыми секундами: при n = 1000 это около ±12 %                                |
| `cc_cpu` (**один** поток) против того же оригинала на 16 потоках                                  | 0,94–2,38×, быстрее в 5 из 6 случаев: переформулировка целевой функции стоит примерно столько же, сколько вся многопоточность оригинала. Обе стороны здесь — медианы по нескольким прогонам                     |
| Качество за фиксированное время                                                                   | GPU за 2 с находит решение лучше, чем `cc_cpu` за 40 с. Но популяция при равном времени имеет **оптимум**: около 1 024, а не 4 096 — покупается произведение «итерации × популяция»                             |
| Размер популяции                                                                                  | на CPU строго линеен (наклон 1,00 в лог-лог координатах), на GPU до популяции 256 почти бесплатен и только затем выходит на линейный участок                                                                    |
| Весь процессор                                                                                    | 16 независимых процессов `cc_cpu` дают 7,98× пропускной способности против одного — это измеренный потолок того, что дал бы многопоточный CPU-порт, и на него честно делить отношение времён                    |

Число итераций в замерах времени зафиксировано: ГПСЧ у бэкендов разный по устройству, поэтому при одном сиде они идут
разными траекториями и по-разному упираются в ранний останов.

## Структура

```
include/cc_math.hpp     целевая функция, дельта хода, ГПСЧ; общий код хоста и устройства
include/cc_graph.hpp    граф: биты, генератор по сиду, ввод-вывод, чтение JSON бейзлайна
include/cc_pbils.hpp    параметры, состояние решения (G, размеры, f), PBILS
include/cc_gpu.hpp      объявление GPU-решателя
include/cc_cli.hpp      единый интерфейс командной строки для обоих бэкендов
src/                    реализация CPU + проверки корректности
cuda/                   ядра CUDA и GPU-раннер
```
