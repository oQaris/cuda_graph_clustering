# cuda_graph_clustering — корреляционная кластеризация графа на GPU

Пакет решает задачу **нестрогой k-корреляционной кластеризации**: разбить вершины
графа не более чем на k кластеров так, чтобы число «разногласий» было минимально.
Разногласие — пара вершин, которая соединена ребром, но разнесена по разным
кластерам, или не соединена, но попала в один кластер.

Основной алгоритм — **PBILS** (population based iterated local search) из
[BIGADIL/graph_correlation_clustering](https://github.com/BIGADIL/graph_correlation_clustering),
перенесённый на CUDA и дополненный шагом GWW. Есть и многопоточная CPU-версия с тем же интерфейсом. Пакет
собирается только из файлов этого репозитория.

Также перенесены **NeighborhoodCuda** и **NeighborhoodWithManyLocalSearchesCuda** для k = 2.
Первый перебирает разбиения «вершина и её соседи / остальные», второй запускает локальный поиск
из каждого такого разбиения. Оба выбирают лучший результат; при равенстве — разбиение от вершины
с меньшим номером. В локальном поиске при равном улучшении переносится меньшая вершина.

```bash
./bin/cc_gpu --algorithm NeighborhoodCuda --n 1000 --k 2
./bin/cc_gpu --algorithm NeighborhoodWithManyLocalSearchesCuda --graph graph.txt --k 2 --pop 128
```

По умолчанию `--algorithm pbils`. Для Neighborhood `--pop` задаёт число разбиений в пакете
(не больше n), а `--ls-kernel` выбирает существующее ядро спуска. Перебираются все n вершин,
в том числе в неполном последнем пакете. Параметры итераций, турнира, GWW, возмущения, сида
поиска и лимита времени не используются. Алгоритмы детерминированы; `--graph-seed` по-прежнему
задаёт граф. В CPU-бинарнике эти два алгоритма недоступны.

Перенос использует битовую матрицу, пересчёт G через popcount и ядра спуска этого репозитория
вместо плотных int8-матриц и cuBLAS исходной реализации. Память состояния — O(n · min(n, pop)),
граф занимает O(n²/32) слов. Пересчёт всех начальных разбиений требует O(n³/32) операций со
словами; стоимость локальных поисков добавляется отдельно. Время и память отличаются от
оригинала, но порядок разбиений и правило выбора ходов сохранены.

## Постановка

| Что             | Как                                                                       |
|-----------------|---------------------------------------------------------------------------|
| Число кластеров | не более k, пустые кластеры допустимы; k любое до 64                      |
| Граф            | невзвешенный, неориентированный, без петель                               |
| Размер на GPU   | пока граф и популяция помещаются в память карты: на 16 ГБ ~340 тыс. вершин |
| Целевая функция | число разногласий, минимизация                                            |

## Как это устроено

Целевая функция считается не по парам вершин, а через матрицу связей
G = A·Z (G[v][c] — число соседей v в кластере c):

```
f = m + Σ_c C(n_c, 2) − tr(ZᵀAZ)
Δf(v: a → c) = (n_c − n_a + 1) − 2·(G[v][c] − G[v][a])
```

Выигрыш любого хода считается за O(1), после хода G правится за O(n). Саму G
пакет считает побитово, через popcount по упакованным строкам матрицы смежности.
Арифметика общая для CPU и GPU и лежит в `include/cc_math.hpp`.

**GPU:** один блок CUDA на особь популяции, потоки блока делят между собой вершины
и вместе ищут лучший ход. **CPU:** та же схема, особь получает поток из пула
(`--threads`).

У каждой особи свой поток ГПСЧ, поэтому ответ не зависит от числа потоков, а при
одинаковых параметрах и `--seed` **CPU и GPU проходят одну и ту же траекторию** и
выдают одно и то же решение.

**GWW.** В итерации есть шаг go with the winners, которого у оригинала нет: после спуска худшая доля
R популяции заменяется копиями лучших особей, и возмущение разводит копии в разные стороны. По
умолчанию R = 0,1 (`--gww R`), а `--gww 0` выключает шаг, и тогда PBILS совпадает с оригиналом. GWW 0,1
почти везде, где мы мерили, даёт лучший ответ за то же число итераций, а итерация не дорожает.
Исключение — длинный поиск на плотных случайных графах при k ≥ 5, где GWW после ~100 итераций
застревает. Замеры — в [docs/benchmarks.md](docs/benchmarks.md), раздел 5.

**Большие графы.** До 32 767 вершин элементы G помещаются в 16 бит, и решатель идёт
узким путём. На большем графе он сам переходит на широкий: G 32-битная, а при k = 2 и
k = 3 спуск ведут отдельные ядра, у которых состояние вершины упаковано в одно слово
(e = G[1] − G[0] и метка; три 20-битных счётчика и метка). Узким местом там становится
память: состояние особи занимает мегабайты, и ядро работает быстро, только пока оно лежит
в кэше L2. Поэтому блоков запускается столько, чтобы их состояние помещалось в L2, а особи
раздаются им по очереди. Траектория та же, что у узкого пути и CPU, а узкий путь от
широкого не изменился. Память карты: битовая матрица n²/8 байт и 3–5 КБ на вершину при
популяции 128. Решатель сверяет это со свободной памятью заранее: под WDDM драйвер молча
выносит в ОЗУ всё, что не помещается в карту, и ядра замедляются в разы.

## Сборка

```bash
make            # CPU-часть; GPU-часть, если найден nvcc
make cpu        # CPU-версия и тесты, CUDA не нужна
make gpu        # CUDA-версия (GPU_ARCH=sm_89 make gpu)
make test       # проверки корректности CPU
make test-gpu   # Neighborhood: точное сравнение с CPU-перебором (нужны nvcc и рабочая CUDA-карта)
```

`cc_verify_gpu` проверяет оба алгоритма, метки при равенствах, число ходов, разные размеры
пакетов и все варианты ядер локального поиска. Без CUDA-устройства возвращает код 77
(проверки GPU пропущены).

`GPU_ARCH` должен соответствовать карте, иначе драйвер будет компилировать ядра из
PTX при каждом запуске: `sm_75` Turing, `sm_80` A100, `sm_86` Ampere GeForce,
`sm_89` Ada, `sm_90` Hopper.

### Windows

Нужны **VS Build Tools** (нагрузка «Разработка классических приложений на C++») и
**CUDA Toolkit**. Из окружения `vcvars64.bat`:

```bat
call "C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\VC\Auxiliary\Build\vcvars64.bat"

mkdir bin obj

cl /nologo /O2 /std:c++17 /EHsc /arch:AVX2 /DNDEBUG /Iinclude ^
   src\cc_graph.cpp src\cc_pbils_cpu.cpp src\main_cpu.cpp ^
   /Fe:bin\cc_cpu.exe /Foobj\

cl /nologo /O2 /std:c++17 /EHsc /arch:AVX2 /DNDEBUG /Iinclude ^
   src\cc_graph.cpp src\cc_pbils_cpu.cpp src\cc_verify.cpp ^
   /Fe:bin\cc_verify.exe /Foobj\

nvcc -O3 -std=c++17 -Iinclude --generate-code arch=compute_89,code=sm_89 ^
   -Xcompiler "/O2 /std:c++17 /EHsc /arch:AVX2 /DNDEBUG" ^
   -o bin\cc_gpu.exe cuda\cc_pbils_gpu.cu cuda\main_gpu.cu ^
   src\cc_graph.cpp src\cc_pbils_cpu.cpp
```

## Запуск

```bash
# сгенерировать G(n, p) по сиду и решить
./bin/cc_gpu --n 3000 --density 0.33 --graph-seed 7 --k 3 --pop 128 --runs 10
./bin/cc_cpu --n 3000 --density 0.33 --graph-seed 7 --k 3 --pop 128 --threads 0

# PBILS оригинала, без шага GWW
./bin/cc_gpu --n 3000 --density 0.33 --graph-seed 7 --k 3 --gww 0

# решить граф из файла результатов оригинала или сохранить инстанс для него
./bin/cc_gpu --graph-json path/to/result.json
./bin/cc_gpu --n 600 --density 0.33 --graph-seed 1 --save-graph-json inst.json

# граф по тегам из данных оригинала (data/Tags_*.json): все объекты или выборка по сиду
./bin/cc_gpu --tags data/Tags_nus_wide.json --n 0 --similarity jaccard --threshold 0.5 --k 3
./bin/cc_gpu --tags data/Tags_so.json --n 330000 --graph-seed 7 --k 2

# граф из списка рёбер, например SNAP: номера вершин любые, петли и повторы отбрасываются
./bin/cc_gpu --edges com-dblp.ungraph.txt --k 2
```

Граф по тегам строится так же, как в `TagsGraphFactory` оригинала: ребро, если сходство
наборов тегов (jaccard, cosine, dice или overlap) не ниже порога. Оригинал берёт
случайную выборку объектов, здесь выборку фиксирует `--graph-seed`, а `--n 0` берёт все
объекты. Весь `Tags_so.json` (706 336 объектов) в явном виде не помещается: его битовая
матрица занимает 58 ГиБ.

Реальные графы (SNAP, OGB, Netzschleuder, gnn-benchmark; от 34 до 317 тысяч вершин) скачивает
`docs/real_graphs/download.sh`, в списки рёбер и разметку групп их переводит `prepare.py`, решает `run.py`.
Данные ложатся в `data/real/` (в git не попадают), результаты — в `docs/data/real_graphs.json`. Что это за графы,
откуда они и как построены — в [docs/real_graphs/README.md](docs/real_graphs/README.md).

Все опции — `--help`. Найденное значение целевой функции по умолчанию перепроверяется
пересчётом по парам вершин, а на графах больше 32 767 вершин — по словам строк матрицы
(O(n²/32) на всех ядрах). При расхождении программа завершается с кодом 2.

## Что проверено

* `make test` (`bin/cc_verify.exe` на Windows): 6947 проверок формулы и инкрементальных
  обновлений против определения по парам, пересчёта по словам строк против попарного, графа
  по тегам против попарного построения оригинала, чтения списка рёбер и порядка копий GWW. Раньше проверки проходили
  и под GCC/Clang, код после рефакторинга собран и проверен только под MSVC.
* CPU и GPU при одном `--seed` дают одинаковые f и число итераций, так же и
  `--ls-kernel shared` против `--ls-kernel global`, а при k = 2 и отдельное ядро (`auto`)
  против общего.
* С GWW (`--gww` 0,1, 0,25, 0,5) CPU на 16 потоках и GPU на всех ядрах (`auto`, `global`, `shared`, `wide`)
  проходят одну траекторию при k = 2, 3, 4, 6, при популяции 1 024 и без возмущения; от `--threads` ответ не
  зависит. С `--gww 0` f и число итераций те же, что до появления GWW.
* Широкий путь проходит ту же траекторию: `--ls-kernel wide` против узкого пути и CPU на
  графах до 5 000 вершин, GPU против CPU при n = 34 000 и k = 2, 3, 4, где узкий путь уже
  невозможен. То же на графах по тегам, где у тысяч вершин-близнецов одинаковые Δ и ничьи
  разрешаются на каждом ходе: выборки NUS-WIDE в 20 000 вершин (узкий, широкий, CPU) и 34 000
  (широкий против CPU), k = 2 и 3. Ветка для карт младше sm_80 проверена сборкой только в PTX
  sm_75 с компиляцией драйвером на 4070.
* Узкий путь с появлением широкого не изменился: те же регистры и разделяемая память у
  всех его ядер и то же время (0,99–1,00× на девяти точках).
* Число рёбер графа по тегам совпадает с независимым расчётом для всего `Tags_nus_wide.json`
  при всех 12 сочетаниях меры и порога.
* Ответ CPU-версии не зависит от `--threads`.
* Значение целевой функции совпадает с тем, что выдаёт оригинал на его же инстансах.
* Ядра собраны и запущены на RTX 4070 Ti SUPER (compute 8.9), CUDA 13.3.

## Производительность

Замеры против оригинала, GPU против CPU и работа на больших графах реальных систем (весь
NUS-WIDE, 193 734 вершины; 330 тысяч вершин из данных Stack Overflow), а также качество с GWW и без
него — в [docs/benchmarks.md](docs/benchmarks.md).

## Структура

```
include/cc_math.hpp             целевая функция, дельта хода, ГПСЧ; общий код хоста и устройства
include/cc_graph.hpp            граф: биты, генератор по сиду, ввод-вывод, чтение JSON оригинала
include/cc_pbils.hpp            параметры, состояние решения, PBILS
include/cc_parallel.hpp         пул потоков CPU-части
include/cc_gpu.hpp              объявление GPU-решателя
include/cc_cli.hpp              общий интерфейс командной строки
src/                            CPU-версия и тесты
cuda/cc_pbils_gpu.cu            GPU-решатель: выбор ядер, память, цикл итераций
cuda/cc_gpu_tuning.cuh          параметры запуска ядер, снятые замером
cuda/cc_gpu_common.cuh          общее для ядер: свёртки по варпу и блоку, ключ хода
cuda/cc_population_kernels.cuh  начальные метки, пересчёт G, селекция, возмущение
cuda/cc_local_search*.cuh       ядра спуска: общее, для k = 2 и для k = 3
docs/                           замеры: отчёт, графики, данные, скрипты
docs/real_graphs/               реальные графы: выгрузка, подготовка, запуск
```

Длина строки в коде — 120 символов, стиль задаёт `.clang-format`.
